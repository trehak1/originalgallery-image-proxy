Obrazová proxy pro originalgallery.com – technická zpráva

22. 10. 2026 · Tomas Rehak

Shrnutí

Proxy snižuje přenos stránky /works z 26,1 MB na 5,0 MB a dobu do načtení všech obrázků z 16,6 s na 3,7 s (teplá cache, 50 Mbit/s). Aplikace se přitom nemění.

  • Problém: 5 sponzorovaných děl na výpisu odkazuje přímo na originály z iPhonu (až 6,5 MB, 4117×5008 px) zobrazené v šířce 160 px. Ostatní náhledy jdou přes Supabase render API bez cache, které odpovídá ~1 s na obrázek.
  • Řešení: nginx + imgproxy před aplikací. Obrázky zmenší z originálu, převede do AVIF q55 a uloží do cache. Vše ostatní jde beze změny na origin.
  • Kvalita: q55 je nastavená tak, aby objem obrázků byl poloviční proti WebP q85 (4,1 místo 8,7 MB). Věrnost je mírně pod dnešními náhledy (SSIM 0,942 proti 0,951) při stejném rozlišení 800 px.

Architektura

Proxy tvoří dva kontejnery: nginx (TLS, HTTP/2, routování, disková cache) a imgproxy (libvips, zmenšení Lanczos3, AVIF q55). Stojí před originem a vše kromě obrázků předává beze změny, takže aplikaci není třeba upravovat.

  • Formát: AVIF q55, pokud prohlížeč posílá Accept: image/avif, jinak WebP q55 nebo progresivní JPEG q75. Odpověď nese Vary: Accept, u originálů Vary: Accept, Referer.
  • Kvalita: zmenšuje se vždy z originálu (Lanczos3) a barevný profil (Display P3 z iPhonů) zůstává. q55 je kompromis kvůli polovičnímu objemu dat. Při zobrazené velikosti náhledu na 2× DPR má SSIM 0,942. Dnešní Supabase JPEG q80 má 0,951 a WebP q85 0,966 (8 děl).
  • Proč 800 px na výpisech: náhledy tam mají nejvýš 185 CSS px, takže i při 3× DPR stačí 555 px. Detail díla (542 px + lightbox) a hero na homepage (1300 px) dostanou 2048 px.
  • Bezpečný fallback: když imgproxy obrázek nezpracuje, nginx vrátí originál z originu (error_page … = @origin).
  • Proč ne Varnish: nginx je kvůli TLS a HTTP/2 potřeba tak jako tak a jeho cache vrací HIT za ~5 ms. Varnish by přidal další komponentu bez měřitelného přínosu.

Při MISS stáhne imgproxy originál přes interní nginx :8081, zmenší ho a nginx výsledek uloží; další požadavky na stejnou variantu jsou HIT.

Metodika měření

Měří se stránka /works v headless Chromiu 156 (Playwright 1.64), viewport 1440×900, každý běh s čistým profilem a vypnutou cache prohlížeče. Skript zaznamená TTFB, LCP a událost load. Pak stránku proscrolluje po 900 px, aby se načetly všechny lazy obrázky, a počká, až budou hotové.

  • Přenesená data jsou encodedDataLength z CDP, včetně hlaviček a skriptů třetích stran.
  • Šířka pásma je v Chromu omezená na 50 Mbit/s, pro obě varianty stejně.
  • Latence: proxy běží na localhostu, ale na serveru bude vedle originu. Proto se k jejím požadavkům přičítá naměřené RTT k originu (226 ms).
  • Scénáře: bez proxy, proxy se studenou cache (před každým během vyprázdněná) a proxy s teplou cache. Každý scénář běží jednou.
  • Studená cache je pesimistická: imgproxy zde stahuje originály přes internet (~10 Mbit/s z originu). Na serveru je bude brát z lokální sítě.

  • Data jsou stabilní, časy orientační. Každý scénář měl jeden běh. Přímé načtení všech obrázků kolísalo během dne mezi 8 a 45 s, protože origin posílá data rychlostí ~10 Mbit/s.
  • Studená cache odpovídá prvnímu návštěvníkovi po vyprázdnění cache. LCP a load jsou rychlejší, protože se stahují menší obrázky. Poslední obrázek ale čeká na stažení originálu z originu přes internet.
  • Pass-through funguje: počet požadavků je ve všech scénářích stejný (~80) a imgproxy při měření nehlásil žádnou chybu. TTFB HTML se nemění, protože HTML jde bez cache.

Spuštění a nasazení

Repozitář obsahuje compose.yaml, nginx/ (konfigurace), certs/gen.sh a bench/measure.mjs.

Lokálně:

  1. ./certs/gen.sh vytvoří self-signed certifikát pro originalgallery.com (jen pro PoC).
  2. docker compose up -d spustí nginx na 127.0.0.1:8443 (HTTPS) a :8080 (HTTP). imgproxy je dostupný jen uvnitř Docker sítě.
  3. Celý web je pak přes proxy na http://localhost:8080 v libovolném prohlížeči. Absolutní odkazy na originalgallery.com v HTML, CSS, JS a přesměrováních proxy přepisuje na adresu, přes kterou klient přišel; pro veřejný host je nechává beze změny.
  4. cd bench && npm install && node measure.mjs zopakuje měření.

Na serveru se mění jen prostředí v compose.yaml, konfigurace nginx zůstává stejná:

ProměnnáPoCServer

Dál je potřeba publikovat porty 80/443 místo 127.0.0.1:8080/8443 a dodat skutečný certifikát do certs/. Alternativně nechat TLS na stávajícím balanceru a proxy vystavit jen na HTTP. Aplikace dostane X-Forwarded-For a X-Forwarded-Proto, takže pokud loguje IP klientů, musí těmto hlavičkám věřit. Cache se vyprázdní příkazem docker compose exec proxy sh -c 'rm -rf /var/cache/nginx/img/*' && docker compose restart proxy.

Omezení a další kroky

  • Varianta podle Refereru: bez Refereru (přísné nastavení soukromí) dostane prohlížeč 2048 px, tedy větší, ale ostrý obrázek. Vary: Referer snižuje znovupoužití cache prohlížeče mezi různými stránkami.
  • Kvalita q55 platí i pro detail a lightbox. Pokud bude na zoomu ztráta vidět, stačí zvýšit IMGPROXY_FORMAT_QUALITY. Například avif=65 znamená asi +40 % dat.
  • Invalidace: názvy souborů obsahují časové razítko, takže nový upload má novou URL. Přepsání souboru pod stejnou cestou se projeví až po vyprázdnění cache (30 dní v proxy, 7 dní v prohlížeči).
  • První návštěva nového díla čeká na stažení originálu. Na serveru v lokální síti to bude zlomek dnešních sekund. Cache jde předehřát průchodem výpisů.
  • Systémově by aplikace měla i u sponzorovaných děl používat render URL. Proxy by pak řešila jen cache a formát, bez heuristiky podle Refereru.
